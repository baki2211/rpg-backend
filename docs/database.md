# Database

> Postgres schema, migration strategy, and conventions for SQL written by hand.

## Engine

- **Postgres 12+** (Docker image is `postgres:12`).
- TypeORM 1.0 with `pg` driver. Pool configured in `src/data-source.js` (max 10, min 2, idle 30s).
- In production the driver runs with `ssl: { rejectUnauthorized: false }`.

## Schema Source of Truth

The TypeORM `EntitySchema` files in `src/models/*.js` are the live source. `AppDataSource` in `src/data-source.js` registers them all. Generated migrations in `src/migrations/` ship the schema to non-dev environments.

When `NODE_ENV === 'development'`, TypeORM has `synchronize: true` — it pushes entity changes straight to the DB on boot. Convenient locally, **dangerous anywhere else**. Other NODE_ENV values default to `synchronize: false`; override with `DB_SYNC=true|false` if you ever need to flip it without changing `NODE_ENV`.

## Conventions

- **Column naming is camelCase** (TypeORM default for `EntitySchema`): `"userId"`, `"createdAt"`, `"isEvent"`. Always quote in hand-written SQL — unquoted identifiers get folded to lowercase by Postgres and won't match. Example:
  ```sql
  -- Right
  SELECT "userId", "createdAt" FROM characters WHERE "userId" = $1;
  -- Wrong (Postgres folds to lowercase; "userid" / "createdat" don't exist → error)
  SELECT userId, createdAt FROM characters WHERE userId = $1;
  ```
- `id` columns are `integer generated by default as identity`.
- Timestamps are `timestamptz`, defaulted to `now()`.
- The migration installs a `set_updated_at()` trigger function in the `public` schema; tables that need it attach the trigger in the migration. New entities that need `updatedAt` auto-touched should also attach this trigger.
- JSONB is used for tunable shapes: `skills.requiredStats`, `skills.scalingStats`, `skills.unlockConditions`, `skills.mutationOptions`.

## Roles Constraint

`users.role` has a check constraint: `('user','staffer','master','admin')`. Adding a new role requires updating:
- the check constraint (or removing it)
- `requireRole(...)` calls across `routes/`
- the role logic in services that branch on role

## Migrations

`src/data-source.js` loads `./src/migrations/*.js`. In order:

| Migration | Kind | What |
|---|---|---|
| `InitialBaseline` | schema | full schema as of the switch to migrations |
| `AlignSkillRuleRows` | data | sets seeded `mastery_tiers` and `MASTERY_TIER_*` / `OUTCOME_*` rows to the code defaults |
| `OneActiveCharacterPerUser` | data + index | deactivates extra active characters per user (keeps the one `getActiveCharacter` reads), then a partial unique index enforces one |
| `StripUnknownCharacterStats` | data | removes `characters.stats` keys no stat definition knows (keeps derived keys) |

Run `npm run migration:run` on a seeded DB **before** starting code from this version; the data
migrations change what the code reads.
- `package.json` exposes:
  - `npm run migration:run`
  - `npm run migration:revert`
- `npm run migration:generate -- src/migrations/<Name>` (against `rpg_baseline`, see below).
- The TypeORM CLI is invoked directly (no build); the scripts pass `--experimental-specifier-resolution=node` because the project is ESM.

See [`migrations.md`](migrations.md) for the full workflow: generating against `rpg_baseline`, hand-review, round-trip verify, applying on the VPS, and rollback.

## Seed Data

`src/jobs/seed.js` fills an empty DB and exits early if any user exists: an `admin` and a normal user
(credentials in the file), stat definitions, a race, a main map and location, three skill branches,
three skill types and their skills, 8 ranks, a character per user with skills, a session with a chat
message, and wiki sections/entries. Built for dev; read it before running anywhere else.

Run via `npm run seed` or in Docker: `docker compose exec app node src/jobs/seed.js`.

`seed.js` does not fill `combat_constants`, `mastery_tiers` or `skill_validation_rules`. An admin creates
the defaults with `POST /api/{combat-constants,mastery-tiers,skill-validation-rules,stat-definitions}/initialize`
(or `scripts/initialize-combat-constants.js`). Without the rows the engine uses the code defaults.

## Static-Data Cache

After editing a cached table (races, skills, branches, types, stat definitions, ranks, combat constants,
mastery tiers) in SQL, call `POST /api/admin/cache/reload[/:entity]` or restart; see
[`architecture.md`](architecture.md#cross-cutting-subsystems).
